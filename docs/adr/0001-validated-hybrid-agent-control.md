# Use an LLM-centered agentic loop with deterministic guardrails

When model access is available, an LLM is the semantic core of the Shopping Agent: it interprets each turn, proposes Constraint State changes, selects Retrieval Routes and clarifications, and may rerank and word the response through an agentic tool loop. Deterministic code supplies the tools and guardrails: it preserves state history in memory under the evaluator's `session_id`, validates proposed mutations, enforces turn and catalog rules, applies the Fusion Policy, rejects invalid outputs, and owns the offline fallback. No database is required for the competition path. The connected loop always permits one planning call; a second reranking-and-response call is made only when it is expected to improve an ambiguous result, otherwise the local cross-encoder and deterministic response builder complete the turn. Provider failure, timeout, invalid structured output, or rejected state transitions trigger a bounded retry and then deterministic takeover. Model access remains behind a provider-neutral adapter so the agent is LLM-centered without making valid scoring depend on one provider or network availability.
